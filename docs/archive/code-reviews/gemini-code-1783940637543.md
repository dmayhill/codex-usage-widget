# Codex Usage Widget - Code Review

To ensure this widget stays robust and out of your way during your daily agentic harness workflow, I've reviewed the provided codebase. The `Tkinter` background threading implementation and the native Windows API bindings are handled surprisingly well. 

Here is the breakdown of flagged issues ranked by severity.

## High Severity

* **Missing Single-Instance Lock:** The `codex_usage_widget.py` script does not enforce a single instance via a Windows Mutex. If the launcher scripts fail to kill previous instances, or if a user double-clicks the script manually, multiple overlapping widgets will spawn and corrupt the state file when they attempt to save their coordinates simultaneously.
* **Missing Essential Scripts:** The README documentation and the provided `.cmd`/`.vbs` launchers rely entirely on `install-windows.ps1` and `start-codex-usage-widget.ps1`, but these files are missing from the provided code. The `.vbs` wrapper will fail silently without them.

## Medium Severity

* **State File Race Conditions:** The `save_state()` function reads and writes directly to `codex_usage_widget_state.json`. If a write is interrupted by a system crash or closed abruptly, the JSON file will be corrupted. Implementing an atomic write—writing to a `.tmp` file first, then replacing the original—will prevent layout amnesia.
* **Brittle Binary Pathing:** Hardcoding the fallback `uv` path to `Path.home() / ".local" / "bin" / "codex-cli-usage.exe"` is fragile. Depending on how `uv` was configured, tool binaries are frequently placed in `%APPDATA%\Roaming\uv\tools` or `%LOCALAPPDATA%\uv\tools` on Windows.
* **Silent Failures on Hidden Launch:** In the `__main__` block, the exception handler tries to display a `MessageBoxW`. Because the script is launched via VBScript with a hidden console (`wShowWindow = 0`), if `MessageBoxW` fails to hook into the desktop session for any reason, the application will exit completely silently. Appending errors to a local `crash_log.txt` is highly recommended.

## Low Severity

* **High-Frequency Polling Loop:** The `update_visibility()` function relies on a continuous 250ms polling loop (`VISIBILITY_CHECK_MS`) to query `user32` and `kernel32` APIs. While modern CPUs can handle this, utilizing `SetWinEventHook` to listen specifically for `EVENT_SYSTEM_FOREGROUND` changes would be far more resource-efficient and event-driven.
* **Hardcoded App Store Marker:** The `CODEX_PACKAGE_MARKER = "\\windowsapps\\openai.codex_"` logic in `codex_has_focus()` assumes the Microsoft Store internal package naming convention will remain static. Relying more heavily on the regex title matching is a safer long-term strategy.
* **Generous Subprocess Timeout:** The `subprocess.run` call in `load_usage()` enforces a 30-second timeout. For a desktop widget updating a UI, 30 seconds of hanging on a background thread is too long. Dropping this timeout to 5–10 seconds will make the refresh cycle feel significantly more responsive when the CLI tool stalls.
* **Catch-All Exception in load_state:** The `except (OSError, ValueError):` block in `load_state()` swallows all parsing errors silently. If the user manually edits the JSON file and introduces a syntax error, the script drops their saved location without warning rather than falling back gracefully to the last known good location.
